# Spec v2.4 - Filets de secours (résilience, coffre de ruches, mode secours WinRE)

Date : 2026-08-22. Statut : validée (design approuvé, choix actés). Exécution prévue APRÈS livraison de la v2.3 (passe UX terrain), sur une branche neuve depuis public-main.

## 1. Origine : enseignements d'une intervention réelle (21/08/2026)

Intervention réelle sur un portable en erreur `0xc000014c` (ruche registre SYSTEM corrompue, Windows ne démarre plus). Réparation menée en navette clé USB entre le PC en panne (WinRE uniquement) et un PC sain. Succès complet. Six enseignements structurent cette vague :

1. **La cause racine était détectable des semaines avant.** Disque C: saturé (espace libre négatif rapporté par `fsutil`), la ruche SYSTEM ne se flushait plus depuis 10 jours (LastWriteTime figé alors que SOFTWARE s'écrivait encore). Aucun outil ne le signalait.
2. **Tous les filets Windows étaient morts silencieusement.** Restauration système désactivée (zéro cliché VSS), `RegBack` vide (comportement normal depuis Windows 10 1803), environnement de récupération dépouillé. Personne ne le savait.
3. **Personne n'a de copie saine de ses ruches registre.** La réparation a dû passer par une autopsie binaire du format regf. Une simple copie des ruches datant d'une semaine avant aurait réglé le problème en minutes.
4. **Le remplacement chirurgical de SYSTEM seul préserve la session utilisateur** (la bootkey qui déchiffre le SAM vit dans SYSTEM et ne change jamais après installation). Vérifié en conditions réelles.
5. **Le WinRE réel est très dépouillé.** `findstr`, `vssadmin`, `wmic` absents ; un pipe vers un binaire absent tue un batch net ; les lettres de volumes changent à chaque session. Les scripts de secours doivent être écrits pour le pire WinRE.
6. **Après réparation, le compte Microsoft peut se re-verrouiller** (« appareil hors connexion », PIN refusé) : l'accès au compte du propriétaire (téléphone, mot de passe) doit être vérifié AVANT l'intervention.

Pièges techniques payés et vérifiés pendant l'intervention (chacun devient une contrainte ou un test) :

- `if exist` ne résout PAS les liens `mklink /d` vers `GLOBALROOT` (faux « aucun cliché ») ; le critère de vie d'un cliché est une lecture `dir /b` réelle.
- `type` corrompt un binaire commençant par un BOM UTF-16 ; `copy /b` et `xcopy /h` uniquement pour les ruches et journaux.
- `copy` ignore les fichiers cachés+système (les `.LOG1/.LOG2`) ; `xcopy /h` ou `attrib` d'abord.
- Des parenthèses dans un chemin (`Program Files (x86)`) cassent un bloc `if (...)` batch ; routines `call :label` sans blocs pour tout code manipulant des chemins.
- `reg load` peut REJOUER les journaux et modifier le fichier : jamais sur un original, toujours sur copie.
- Les vérifications d'intégrité se font par taille exacte en octets (pas de hash : `certutil` non garanti en WinRE).
- Sortie console DOS en CP850 : les fichiers produits côté WinRE se relisent avec l'encodage OEM 850 côté PC sain.

## 3. Chantier A - Sentinelle résilience (extension de `00-Diagnostic.ps1`)

Constats en lecture seule, ajoutés à l'objet résultat du diagnostic et rendus dans le rapport HTML avec les niveaux existants (OK / WARN / ERROR).

| Constat | Règle | Niveau |
|---|---|---|
| Espace libre C: | < 20 Go ou < 10 % | WARN |
| Espace libre C: | < 10 Go ou < 5 % | ERROR |
| Fraîcheur ruche SYSTEM | LastWriteTime en retard de plus de 48 h sur SOFTWARE | WARN |
| Fraîcheur ruche SYSTEM | Retard de plus de 7 jours | ERROR (signature pré-crash) |
| Restauration système | Désactivée sur C: ou zéro point présent | WARN |
| Stockage de clichés (shadowstorage) | Non configuré ou inférieur à ~5 % du volume | WARN |
| WinRE | `reagentc /info` en Disabled, ou `recoveryenabled` absent/No dans le BCD | WARN |
| BitLocker | Volume chiffré sans protecteur RecoveryPassword détectable | ERROR |
| BitLocker | Volume chiffré avec protecteur présent | INFO + rappel « vérifiez que la clé est accessible : aka.ms/myrecoverykey » |

Notes d'implémentation :
- Fraîcheur des ruches : lire les LastWriteTime de `C:\Windows\System32\config\{SYSTEM,SOFTWARE}` (accessible en admin). La comparaison relative SYSTEM vs SOFTWARE évite les faux positifs d'un PC éteint longtemps.
- BitLocker : `Get-BitLockerVolume` si disponible, sinon `manage-bde -status` + `-protectors -get C:` parsé. La sentinelle dit honnêtement ce qu'elle ne peut PAS vérifier hors ligne (la sauvegarde de la clé sur le compte Microsoft) : le rapport donne la marche à suivre, il n'invente pas un verdict.
- Chaque constat est calculé dans une fonction pure testable de `lib/` (entrées valeurs, sortie verdict), même approche que `Test-SmartDriveAlert`.

## 4. Chantier B - Nouveau module `16-Resilience.ps1` (« Filets de secours »)

Position : inséré dans le tableau d'exécution JUSTE APRÈS `01-Backup` (les ruches se sauvegardent avant toute modification du système par les modules suivants). L'Id fichier est `16`, la numérotation d'affichage suit la position dans la timeline (mécanique v2.3). Case GUI cochée par défaut dans le profil Standard.

### 4.1 Réarmement des filets (complète `01-Backup` sans doublon)

- `reagentc /enable` si `reagentc /info` répond Disabled.
- `bcdedit /set {default} recoveryenabled Yes` si absent ou No.
- Agrandir le shadowstorage de C: à 5-10 % s'il est configuré en dessous ; **ne JAMAIS le réduire** (réduire purge des clichés existants). `vssadmin resize shadowstorage /for=C: /on=C: /maxsize=10%` uniquement dans le sens croissant.
- Chaque réarmement logue l'état AVANT et APRÈS ; `-WhatIf` complet ; aucun undo nécessaire (actions non destructives, état avant tracé au log).

### 4.2 Coffre de ruches

- `reg save` des 5 ruches : `HKLM\SYSTEM`, `HKLM\SOFTWARE`, `HKLM\SAM`, `HKLM\SECURITY`, `HKU\.DEFAULT` (fichiers SYSTEM, SOFTWARE, SAM, SECURITY, DEFAULT). `reg save` produit une ruche défragmentée propre sans verrou.
- Destinations : `<racine du volume du kit>\Coffre\<COMPUTERNAME>\hives-<yyyyMMdd-HHmmss>\` (la clé USB d'où le kit s'exécute) ET copie locale `C:\ProgramData\PC-Refresh-Kit\HiveVault\hives-<date>\`. Le coffre externe survit à la mort du disque ; le coffre local survit à l'absence de la clé. Si le volume du kit n'est pas amovible (kit copié sur C:), le coffre externe est écrit sur le premier volume externe détecté (même logique que `01-Backup`), sinon coffre local seul + WARN.
- Rotation : 3 jeux conservés par destination, les plus anciens supprimés (suppression tracée au log).
- `manifest.txt` par jeu, ASCII pur, format `cle=valeur` parsable par `for /f` batch :
  `machineid=`, `computername=`, `build=`, `date=`, puis `taille_system=`, `taille_software=`, `taille_sam=`, `taille_security=`, `taille_default=` (tailles exactes en octets, contrôlées après copie).
- Empreinte machine : le module crée (au premier passage) `C:\ProgramData\PC-Refresh-Kit\machine-id.txt` contenant un GUID, et le recopie dans chaque manifeste. C'est la clef de voûte du garde-fou de restauration : en WinRE, `COMPUTERNAME` vaut un MININT-xxx et le registre est cassé ; seul ce fichier posé sur le volume Windows fait foi.

### 4.3 Option BitLocker (décochée par défaut)

- Option GUI « Exporter la clé de récupération BitLocker dans le coffre » : DÉCOCHÉE par défaut, avertissement explicite dans l'aide (« la clé écrite en clair sur la clé USB ouvre le disque ; conservez la clé USB comme un trousseau »).
- Si cochée et volume chiffré : écrit `bitlocker-recovery.txt` dans le coffre EXTERNE uniquement (jamais dans HiveVault local, qui vit sur le disque qu'il est censé déverrouiller).

## 5. Chantier C - Mode secours WinRE (`secours.bat`)

Un seul fichier à la racine de la clé du kit + un dossier `secours\` créé par le script pour ses sorties. Une seule commande courte à taper côté PC en panne (exemple : `e:\secours.bat`).

### 5.1 Contraintes non négociables (héritées du terrain, testées par CI)

1. ASCII pur (aucun octet > 0x7F), CRLF, aucun accent dans les textes (exception batch DOS assumée et documentée).
2. Zéro pipe `|`.
3. Zéro binaire hors liste blanche : builtins cmd + `reg`, `xcopy`, `attrib`, `chkdsk`, `fsutil`, `wpeutil`. Tout autre exe est interdit (`findstr`, `vssadmin`, `wmic`, `choice`, `certutil` : absents des WinRE dépouillés). `wpeutil` n'est jamais exécuté par le script (seulement affiché en consigne finale).
4. Aucune lettre de volume codée en dur : clé = `%~d0` ; volume Windows = celui qui porte `\Windows\System32\config\SAM` (boucle de lettres SANS X:, le ramdisk WinRE) ; départage multi-volumes par `machine-id.txt` si le coffre est présent.
5. Erreurs toujours visibles : jamais de `>nul 2>&1` sur une commande dont l'échec change le diagnostic ; tout va au log (`%~d0\secours\secours.txt`).
6. Menu par lettres via `set /p` (builtin) ; `pause` final systématique ; progression à l'écran via `>con` quand le corps est redirigé au log.
7. Routines `call :label` sans blocs `if (...)` autour des manipulations de chemins (piège parenthèses).
8. Binaires copiés en `copy /b` / `xcopy /h` exclusivement ; jamais `type` ; intégrité par taille exacte.
9. Crochets de test par variables d'environnement `SECOURS_FORCE_WIN` et `SECOURS_DRYRUN` (préfixe `%DO%`), inertes en usage réel.

### 5.2 Menu `[D]` Diagnostic (lecture seule sur le volume Windows)

- Détection et affichage des volumes ; abandon propre si volume Windows introuvable, avec dump des racines de toutes les lettres visibles dans le log (aide au diagnostic à distance).
- Détection BitLocker : si aucun volume ne porte `config\SAM` mais qu'un volume verrouillé/RAW est visible, message guidé au lieu d'un échec muet. La consigne affichée s'adapte à la présence de `manage-bde.exe` dans ce WinRE (testée par `if exist`, le script ne l'exécute jamais : il n'a pas la clé) : commande de déverrouillage à taper soi-même, sinon renvoi vers aka.ms/myrecoverykey.
- État des 5 ruches + journaux : `dir /a` de `config` et `config\TxR` (dates et tailles : le gel de SYSTEM se lit là).
- `fsutil volume diskfree` (la saturation, cause racine type).
- Sondage VSS 1..30 via `mklink /d` vers `GLOBALROOT` : critère de vie = lecture `dir /b` en `for /f` (JAMAIS `if exist`), `rmdir` du lien entre essais, comptage et listing de `config` de chaque cliché vivant.
- Dumps `dir /s /a` ciblés vers `secours\` : racine, System Volume Information, Users, Windows, Program Files, Program Files (x86), ProgramData.
- Inventaire de l'outillage du WinRE courant (`dir /b X:\Windows\System32\*.exe` vers un fichier de `secours\`) : la navette sait quels outils ce WinRE possède avant d'écrire la suite.
- Trace `diagfait.txt` dans `secours\` (horodatée) : le menu `[R]` la vérifie.

### 5.3 Menu `[S]` Sauvetage (copie de l'état cassé vers la clé)

- Copie `xcopy /h` des 5 ruches + `.LOG1/.LOG2` + dossier `TxR` vers `secours\etat-casse\`, vérification par tailles, listing final.
- Aucune écriture sur le volume Windows.

### 5.4 Menu `[R]` Restauration guidée depuis le coffre

Garde-fous, dans l'ordre, chacun bloquant :
1. Coffre présent sur la clé (`Coffre\*\hives-*\manifest.txt`), sinon refus avec explication.
2. `machine-id.txt` du volume Windows détecté == `machineid=` du manifeste. Mismatch = refus ferme (« ce coffre vient d'un autre PC »). Absence du fichier côté volume = refus (jamais posé par le kit sur ce PC).
3. Diagnostic `[D]` exécuté au préalable dans la session de menu courante (comparer des dates en batch est fragile, leçon du 21/08 ; `diagfait.txt` reste écrit comme trace horodatée pour la navette), sinon refus avec consigne de le lancer d'abord.
4. Jeu retenu : le plus récent dont l'empreinte machine concorde (les plus anciens restent posables à la main, procédure documentée) ; choix de la ruche (SYSTEM par défaut, le cas `0xc000014c`).
5. Taille du fichier du coffre == taille du manifeste, sinon refus (« coffre corrompu »).
6. Confirmation en toutes lettres : l'utilisateur tape `OUI` (set /p, comparaison exacte).

Séquence de pose (éprouvée) :
1. `chkdsk <WINVOL> /f` ; code retour >= 3 = arrêt, rien n'est posé.
2. `copy /b /y` de la ruche en place vers `<ruche>.casseN` (N incrémenté si existant).
3. Pose `copy /b /y` depuis le coffre ; contrôle de taille à l'octet près ; en cas d'écart, remise en place immédiate de la sauvegarde `.casseN` et message d'erreur.
4. `attrib -s -h` puis `ren` des `.LOG1/.LOG2` de la ruche posée en `.casse` (journaux dépareillés jamais rejoués ; Windows les recrée).
5. Consignes finales à l'écran ET au log : retirer la clé, taper `wpeutil reboot` ; après redémarrage réussi, relancer le kit côté Windows (rapport + re-sauvegarde du coffre).

### 5.5 Fabrication et déploiement

- `secours.bat` vit à la racine du repo (cohérence avec les `Lancer-*.bat`) et est déployé à la racine du zip de release.
- Le fichier est écrit et versionné en ASCII strict ; la CI le vérifie octet par octet (chantier E).

1. **Test Pester statique des batch de secours** (nouveau `tests/Secours.Static.Tests.ps1`) : pour `secours.bat` (et tout futur .bat WinRE) : zéro octet > 0x7F ; CRLF strict ; zéro `|` ; zéro exe hors liste blanche (analyse des tokens de commande) ; zéro lettre de volume codée en dur hors variables ; `pause` présent avant chaque `exit /b` terminal ; boucles de lettres sans X:. Chaque piège payé le 21/08 devient une assertion permanente.
2. **Dry-run CI** : exécution de `secours.bat` en `SECOURS_FORCE_WIN` + `SECOURS_DRYRUN` sur le runner (parcours D, S et R traversés sans action) ; sortie contrôlée (sections présentes, zéro pose réelle).
3. **Unitaires lib** : fonctions pures de la sentinelle (seuils espace, fraîcheur ruches, verdicts BitLocker/WinRE) et du coffre (rotation, manifeste, parse).
4. **SelfTest GUI** (`Run-GUI.ps1 -SelfTest`) étendu : case module 16 présente, profils l'incluent, option BitLocker décochée par défaut, divergence vers (personnalisé) correcte.
5. **Anonymat** : `Test-KitAnonymity` (-CI et -History avant publication) ; AUCUNE trace de l'intervention réelle dans le repo (aucun nom d'utilisateur réel, aucun PIN, aucun contexte personnel) ; tout le code produit est réécrit générique depuis les patterns, jamais copié tel quel.
6. Contraintes projet inchangées : JAMAIS exécuter le kit en réel sur le PC de dev ; PS1 en BOM UTF-8 ; zéro U+2014/U+2013 ; commits ASCII ; vendor/TelemetryGuard intouchable ; Run-GUI via powershell.exe 5.1.

## 9. Hors périmètre v2.4 (explicite)

- Toute purge disque côté WinRE (le `nettoyage.bat` du 21/08 était spécifique à une machine diagnostiquée ; une purge générique aveugle est exclue du produit).
- Réparation binaire regf automatisée dans `secours.bat` (reste un acte expert outillé par `tools/regf/`).
- Restauration de SOFTWARE/SAM/SECURITY par défaut (possibles via `[R]` mais SYSTEM est le défaut guidé ; les autres exigent la même procédure et affichent un avertissement supplémentaire : désynchronisation possible applications/comptes).
- Déplacement de données utilisateur, gestion OneDrive côté WinRE.
- Support des ruches d'un autre PC (mismatch machine-id = refus, pas de mode « je sais ce que je fais »).

## 10. Critères d'acceptation

1. Sur un PC sain avec la clé : le module 16 produit un coffre complet (2 destinations, 5 ruches, manifeste exact, rotation à 3), réarme WinRE/restauration/shadowstorage si besoin, et le rapport HTML affiche les constats sentinelle.
2. `secours.bat` en dry-run traverse D, S, R sans une seule écriture hors de `secours\` et du log.
3. Le garde-fou machine-id refuse un coffre étranger (testé en CI avec deux GUID distincts).
4. La restauration refuse : coffre absent, diag absent, taille discordante, confirmation autre que `OUI` (4 tests).
5. Les tests statiques batch passent, et une violation volontaire de chaque règle (pipe, exe interdit, octet non-ASCII, lettre en dur) fait échouer le test correspondant (auto-vérification de l'oracle, leçon v2.3).
6. `Test-KitAnonymity -CI` passe ; grep du repo sans aucune trace de l'intervention source.
7. SelfTest GUI vert avec le module 16 ; captures relues (garde-fou v2.3).
