# v2.5 Confiance visuelle - Design

## Contexte et objectif

Deux peurs exprimées en regardant le cockpit (par le créateur du kit, donc a fortiori par un
client) : « la sauvegarde des données fait peur, les données sont-elles en danger ? » et « le
mode agressif désinstalle-t-il toute app non utilisée depuis 3 mois ? ». L'audit du code montre
que le fond est sain (copie additive robocopy, périmètre debloat fermé à 5 groupes d'apps
Store), mais que les réponses aux deux questions universelles - « qu'est-ce que je risque ? »,
« est-ce réversible ? » - existent uniquement en texte, dans une aide qu'il faut survoler.

Fait aggravant vérifié : la GUI lance tous les modules avec `-Unattended` (`lib/Common.ps1:536`),
donc la branche PROMPT de `Get-DebloatDecision` n'existe jamais depuis le cockpit : en politique
Standard, une app conditionnelle non utilisée depuis 90 jours est supprimée sans question.

Objectif : le kit se justifie d'un coup d'oeil. Trois volets :

1. Un ancrage visuel qui relie l'aide affichée à l'élément de l'interface concerné.
2. Un en-tête contextuel avec badges normalisés (réversibilité, données perso, durée) en tête
   du panneau d'aide.
3. Une passe confiance sur les trois points anxiogènes relevés : filet de sauvegarde visible,
   vérité du cockpit annoncée avant le Go, micro-copie des libellés qui portent seuls.

Décisions utilisateur (28/08) : approche « ancrage + badges » retenue (pas de mini-carte, pas
de vignettes) ; vague confiance complète incluse. Version cible : v2.5.0 (feature, mineure).

## A. Ancre visuelle (lien élément - aide)

L'élément dont l'aide est actuellement affichée porte un marqueur visuel tant que l'aide
affichée est la sienne, y compris pendant le gel et l'épinglage.

- `New-KitModuleRow` (lib/Theme.ps1:423) gagne un contrôle enfant `AnchorStripe` : Panel fin
  (3 px de large, hauteur de la ligne, bord gauche), couleur Accent de la palette,
  `Visible = $false` par défaut. Exposé dans le PSCustomObject retourné (ajout additif).
- Nouvelle fonction Theme `Set-KitRowHelpAnchor -Row <row> -On <bool>` : montre/cache le
  liseré. Orthogonale à `Set-KitModuleRowState` : aucun état d'exécution ne touche
  `AnchorStripe`, l'ancre survit à Pending/Queued/Running/Ok/etc.
- Côté GUI : au point central où le panneau d'aide est effectivement remplacé (décision `Show`
  de `Get-KitHelpDecision`, dans `Show-KitHelp`), si la clé affichée est `module.NN`,
  retrouver la row par Id et poser l'ancre ; retirer l'ancre précédente dans tous les cas
  (une seule ancre à la fois, état dans `$script:HelpAnchorId`). Clés non-module : pas
  d'ancre de ligne, l'en-tête (volet B) identifie l'élément. Retour à l'accueil : ancre retirée.
- Épinglage/gel : l'aide ne change pas, donc l'ancre ne bouge pas - aucun code spécifique.

## B. En-tête contextuel + badges du panneau d'aide

Bande dockée en tête de l'onglet Aide, même pattern de docking que le bandeau d'épinglage
existant (Run-GUI.ps1:415 : le RichTextBox est ajouté en premier pour que le docking empile
correctement - conserver cet ordre). De haut en bas : bandeau d'épinglage (existant), en-tête
contextuel (nouveau), RichTextBox (existant, Fill).

- Ligne 1 : badge de type coloré + fil d'Ariane en couleur discrète (InkMuted).
- Ligne 2 : badges normalisés (0 à 3 selon les données disponibles). Si aucune donnée de badge
  et clé inconnue, l'en-tête se réduit à la ligne 1 avec le repli « AIDE / Général ».
- Le corps RichTextBox est inchangé (`Format-HelpPanel` intact, titre compris) : les badges
  résument, le texte garde la nuance.

### Fonctions pures (lib/Help.ps1)

`Get-HelpHeaderInfo -Key <string>` retourne `@{ Kind; KindText; Breadcrumb }` :

| Préfixe de clé | KindText | Breadcrumb |
|---|---|---|
| `module.` | `ÉTAPE` | `Intervention > Étapes` |
| `profile.` | `PROFIL` | `Intervention > Profil` |
| `debloat.` | `RÉGLAGE` | `Réglages > Débloatage` |
| `account.` | `RÉGLAGE` | `Réglages > Comptes` |
| `action.` | `ACTION` | `Actions` |
| autre | `AIDE` | `Général` |

Le plan complétera la table après inventaire des préfixes réellement présents dans
`config/help.fr.json` (toute clé non couverte tombe sur le repli, jamais d'erreur). Le numéro
d'étape n'apparaît pas dans le badge : le `title` du catalogue le porte déjà (« Étape 2 - ... »)
et la colonne timeline n'affiche jamais l'identifiant technique du fichier module.

`Get-HelpBadges -Entry <object>` retourne une liste de `@{ Text; Level }` à partir du champ
optionnel `badges` de l'entrée (voir volet D). `Level` pilote la couleur via la palette
(Ok, Accent, Warn, Error, neutre). Mapping :

| Champ | Valeur | Texte badge | Level |
|---|---|---|---|
| reversible | `yes` | `RÉVERSIBLE` | Ok |
| reversible | `store` | `RÉVERSIBLE VIA STORE` | Accent |
| reversible | `partial` | `PARTIELLEMENT RÉVERSIBLE` | Warn |
| reversible | `no` | `IRRÉVERSIBLE` | Err |
| reversible | `readonly` | `LECTURE SEULE` | Ok |
| data | `untouched` | `DONNÉES PERSO : INTACTES` | Ok |
| data | `copyonly` | `DONNÉES PERSO : COPIE SEULE` | Accent |
| data | `optin` | `DONNÉES PERSO : OPT-IN CORBEILLE` | Warn |
| duration | texte libre court | `DURÉE : <texte>` | neutre |

Champ `badges` absent, sous-champ absent ou valeur inconnue : le badge correspondant est
simplement omis, jamais d'erreur (même contrat fail-safe que le reste du catalogue).

## C. Fil d'Ariane : dérivé des clés, zéro donnée nouvelle

Couvert par `Get-HelpHeaderInfo` ci-dessus. Aucun champ nouveau dans le catalogue pour le
breadcrumb, aucune maintenance de position : la clé suffit.

## D. Données : champ optionnel `badges` dans config/help.fr.json

```json
"module.03": {
  "title": "Étape 5 - Désencombrement : applications préinstallées",
  "badges": { "reversible": "store", "data": "untouched", "duration": "5-15 min" },
  ...champs existants inchangés...
}
```

- Les trois sous-champs sont optionnels et normalisés (enums du volet B, `reversible` acceptant
  aussi `readonly` pour les modules en lecture seule ; champ absent = pas de badge, il n'y a
  pas de valeur `na` ; `duration` : texte court, le champ existant `duration` du corps garde
  la version longue).
- Couverture initiale : toutes les entrées `module.*` reçoivent les trois sous-champs
  (`data` = `untouched` partout sauf module 01 `copyonly` et module 07 `optin`) ; les
  entrées réglages/actions seulement là où un badge a du sens (pas de durée pour un réglage).
- Contrainte encodage existante : `config/*.json` sans BOM.

## E. Vague confiance

### C1 - Filet de sauvegarde visible

- Extraction DRY : la détection des volumes candidats de `modules/01-Backup.ps1:96-108`
  (filtres + tri amovible d'abord) devient `Select-KitBackupCandidates -Volumes <objets>`
  (pure, testable sur volumes simulés : filtre lettre, exclusion disque système, tri
  Removable avant Fixed) + wrapper fin `Get-KitExternalBackupVolumes` qui appelle
  `Get-Volume` (lib/Common.ps1). Le module 01 consomme le wrapper, comportement identique.
- Indicateur permanent dans la barre d'action, à droite du résumé live (le layout existant de
  la barre le recale ; visible en phase préparation, masqué pendant et après le run), états
  combinant « module 01 et option données cochés » et « volume détecté » :
  - amovible détecté : `Filet de sauvegarde : disque <L>: (<X> Go libres)` - vert Ok ;
  - partition fixe seulement : `Filet : partition interne <L>: - vérifier que c'est bien un
    disque externe` - orange Warn ;
  - aucun volume : `Aucun disque externe : les fichiers personnels ne seront pas copiés` -
    orange Warn ;
  - module 01 décoché (prioritaire) : `Étape sauvegarde décochée : aucun filet données` -
    orange Warn.
- Rafraîchissement : au chargement, sur `Form.Activated` (avec garde anti-rafale, pas plus
  d'une détection toutes les 2 s) et au clic Go avant le récapitulatif.
- Le récapitulatif pré-lancement reprend l'état du filet (voir C2, même dialogue).

### C2 - Vérité du cockpit avant le Go

- Constat vérifié pendant la planification : il n'existe AUCUN dialogue de confirmation
  pré-lancement (le clic LANCER enchaîne directement). La vague en crée un, CONDITIONNEL :
  une fonction pure `Get-KitPreRunWarnings -BackupState -Module03Checked -Policy -IsDryRun`
  rend la liste des lignes à annoncer - filet dégradé (aucun disque, partition interne,
  sauvegarde décochée) et suppression silencieuse du débloatage (Standard : apps douteuses
  non utilisées depuis 90 j supprimées sans question ; Agressif : supprimées même utilisées).
  Liste vide = aucune modale (rien à signaler = aucune friction) ; en simulation, jamais de
  confirmation. Si la liste n'est pas vide : une MessageBox Oui/Non unique avant Build-Queue.
- Catalogue : `debloat.standard` réécrit pour dire explicitement que depuis le cockpit la
  suppression se fait sans question (la question n'existe qu'en ligne de commande interactive).

### C3 - Micro-copie

- Ligne de conséquence dynamique sous la ComboBox de politique de débloatage (label InkMuted,
  mis à jour sur SelectedIndexChanged), via une fonction pure `Get-DebloatPolicyHint` :
  - Conservateur : `Ne supprime aucune app douteuse` ;
  - Standard : `Garde tout ce qui a servi depuis 90 j ; le reste est retiré sans question` ;
  - Agressif : `Supprime les apps douteuses même utilisées (sauf Game Pass)`.
- Passe catalogue (contenu seul, aucun renommage d'identifiant : profils, logs, rapports
  intacts) :
  - `module.01` : le `short` commence par la nature de l'opération (« Copie vos dossiers
    personnels - jamais déplacés ni supprimés - ... ») et le `what` répond au POURQUOI :
    le point de restauration Windows ne protège pas les fichiers personnels, et une copie
    sur le même disque mourrait avec lui ; le disque externe est le seul filet qui survit
    à une panne pendant l'intervention.
  - `module.03` : le `short` précise « liste fermée d'applications préinstallées, jamais vos
    logiciels installés ».
  - `debloat.standard` : vérité cockpit (cf C2).
  - Relecture rapide de tous les `short` restants avec l'angle « qu'est-ce que je risque ? »
    (retouches mineures seulement).

## F. Hors périmètre

Mini-carte de l'interface, vignettes illustrées, émojis/glyphes décoratifs dans l'UI, watcher

traductions, `C:` en dur restants hors modules déjà traités (réserve existante).

## Tests et qualité

- Pester (pwsh uniquement) :
  - `Help.Tests.ps1` : `Get-HelpHeaderInfo` (chaque préfixe + repli), `Get-HelpBadges`
    (enums valides, valeur inconnue ignorée, champ absent = liste vide, entrée sans
    `badges` = liste vide) ; non-régression des décisions épinglage/gel.
  - `Theme.Tests.ps1` : `New-KitModuleRow` expose `AnchorStripe` (invisible par défaut) ;
    `Set-KitRowHelpAnchor` on/off ; `Set-KitModuleRowState` ne modifie pas `AnchorStripe` ;
    `Get-KitPreRunWarnings` (simulation, états de filet, politiques, cumul) ;
    `Get-DebloatPolicyHint` (3 politiques + inconnue) ;
    textes du filet C1 (fonction pure de formatage, 4 états).
  - `Common.Tests.ps1` : `Select-KitBackupCandidates` sur volumes simulés (exclusion système,
    tri amovible d'abord, aucun candidat) ; concordance version v2.5.0.
- SelfTest GUI (powershell 5.1, `Run-GUI.ps1 -SelfTest`) étendu : en-tête contextuel présent,
  badges rendus pour une clé qui en porte, ancre posée après affichage de l'aide d'un module
  puis retirée au retour à l'accueil, indicateur filet présent avec un texte d'un des états.
- Portes existantes toutes vertes : parse, encodage (la spec et les .md ont le BOM ; les
  .json n'en ont pas), anonymat, smoke, Pester complet, SelfTest.
- Version : `Get-KitVersion` = `v2.5.0`, `Build-ReleaseZip` = `2.5.0`, test de concordance
  mis à jour. Notes de release à la publication uniquement.

## Exécution

Branche `feat/v2.5-confiance-visuelle` (locale, jamais poussée - règle des branches
granulaires). Implémentation par subagents (subagent-driven development), un commit atomique
par tâche, portes complètes après chaque tâche, revue whole-branch finale, puis squash vers
`public-main` et release v2.5.0 après accord explicite.
